## Findings

### RED — Redundancy and merge candidates
- **RED-1** (medium, new) Topic administration takes up 7 of 30 tools: `set_topic_sharing`, `get_topic_members`, `set_topic_member`, `list_topic_tokens`, `create_topic_token`, `rotate_topic_token`, `revoke_topic_token`. Together they are 2909 tools/list chars. Chat clients rarely need them, and the web Share/Connect UI already covers them. Evidence: inventory table; `services/topic_tools.ts:49-62`. Recommendation: merge the four token tools into one `manage_topic_token(action: list|create|rotate|revoke)`, merge the member tools into `topic_access(action)`, or keep these tools only for personal tokens and leave them out of chat-oriented grants.
- **RED-2** (low, new) `s2_citations` and `s2_references` share the same schema and differ only in direction. Evidence: `agent_tools.ts:775-785`. Recommendation: one `s2_graph(id, direction, limit, offset)`.

### DESC — Description quality and size
- **DESC-1** (medium, new) `upload_image` has a 747-char description aimed at Paperland's own Codex runs: the `$CODEX_HOME/generated_images/` path, a `curl` recipe and the agent-only `path` parameter. External clients such as ChatGPT cannot use any of this, and they all receive it. Evidence: `agent_tools.ts:800-813`; `path` only works for agent tokens (`agent_tools.ts:498`). Recommendation: move the Codex-specific guidance into the Codex run prompt (`agent_attach.ts`), and keep the public description under about 250 chars.
- **DESC-2** (low, new) The initialize `instructions` (1056 chars) mix Topic schema editing, paper writes, blog import and image upload in one paragraph, and they name token-kind rules that the tool descriptions repeat. Recommendation: organize them as short task-oriented lines (find/read papers → add papers → Topics) and leave per-tool details to the descriptions.

### PARAM — Parameters and schemas
- **PARAM-1** (medium, new) `read_pdf_page` accepts `offset` and `max_chars`, but they have no description, and the tool description does not mention page-text pagination. The schema returns `next_offset`, so models cannot tell that a long page continues. `region` also has no description. Evidence: inventory schema; `pdf_pages.ts:13,40-43`.
- **PARAM-2** (low, new) The same concepts use different names across tools: `pdf_data` (add_paper) vs `data` (upload_paper_pdf), `pdf_url` vs `url`, and `id` (S2 edge tools) vs `paper_id`. Strictness also varies: Topic tools and `read_pdf_page` set `additionalProperties: false`, the paper and S2 tools do not. Neither `upload_image` (`path|url|data`) nor `add_paper` (identifier vs manual title+link) expresses its exclusive alternatives in the schema. Recommendation: align names when touching these tools, and add `additionalProperties: false` throughout.

### PERM — Token kinds and permissions
- **PERM-1** (medium, new) `tools/list` is the same for every token kind, but many tools fail by kind. Topic tokens are refused by every unrestricted write tool (`agent_tools.ts` callAgentTool: "Topic credentials cannot use unrestricted write tools") and by all `personal()`-gated Topic admin tools. Agent tokens are refused by the paper write tools (`requirePersonal`). A Topic token therefore sees about 15 tools it can never call. Evidence: inventory "identical for all: yes"; `topic_tools.ts:12-14`; `agent_tools.ts:557`. Recommendation: filter `tools/list` by what the authenticated grant can call. This becomes mandatory once OAuth grants with scopes exist.
- **PERM-2** (high, new) There is no permission tier for destructive operations. Deleting papers and deleting Q&A answers is not exposed over MCP at all. The developer wants chat clients (ChatGPT) to have full write access, with deletion of papers and answers granted separately. Today the only distinction is the token kind, so a destructive scope cannot be expressed. Recommendation: introduce grant scopes (read, write, delete) alongside OAuth. Add delete tools only behind the delete scope, and annotate them `destructiveHint: true`.

### ANN — Annotations
- **ANN-1** (low, new) `add_paper` returns the existing paper with `created=false` when it is already present. That makes it effectively idempotent, but it is annotated `idempotentHint: false`. Evidence: `agent_tools.ts:705` (`WRITE_ANNOTATIONS`), add_paper description. Recommendation: set `idempotentHint: true`.
- **ANN-2** (low, new) `list_topic_tokens` is annotated `readOnlyHint: true` but carries the internal `write: true` flag, which is used to gate personal-only tools. The internal flag conflates "needs a personal token" with "writes". Evidence: `topic_tools.ts:55`. Recommendation: split it into separate `personal_only` and `write` flags.

### SIZE — Response size and pagination
- **SIZE-1** (medium, new) Every `get_topic` call embeds the full `repository_contract` (`topicSchemaContract()`), duplicating `get_topic_schema`. A call without `document` also returns the whole numbered reference catalog (98 current entries for Topic 3). Evidence: `topic_tools.ts:43-44`. Recommendation: return only `repository_schema` status by default, and add an `include_contract` flag, or point to `get_topic_schema`.

### ERR — Errors, not-ready states and fallbacks
- **ERR-1** (high, new) `read_paper` stops at a dead end while doc2x parsing is pending: `Paper N has no full text (not parsed yet)`. It offers no fallback, even though the PDF exists and `read_pdf_page` can already extract page text locally with pdftotext. The developer wants a rough, non-precise parse returned instead, labeled as such, plus a pointer to arXiv HTML for arXiv papers. The model should also be told to check again on the user's next question. Evidence: `agent_tools.ts:229-232`; `pdf_pages.ts:37`.
- **ERR-2** (medium, new) `get_paper` reports `full_text: null` and nothing else. It does not include the PDF/parse pipeline status that `add_paper`/`update_paper` already return through `pdfStatusOf`. `refresh_paper` says "check get_paper later", but `get_paper` cannot show progress. Evidence: `agent_tools.ts:181-206` vs `writtenPaper` at `agent_tools.ts:589-606`. Recommendation: include the PDF and parse status in `get_paper`, `search_papers` and `add_paper`, with a `next_step` hint for each state.

### COMPAT — Client compatibility
- **COMPAT-1** (high, new) ChatGPT custom MCP connectors support only OAuth or no authentication, so a static `Authorization: Bearer` token cannot be configured. Paperland's `/mcp` only accepts static API tokens and answers 401 with a bare `WWW-Authenticate: Bearer` and no `resource_metadata`. No `/.well-known/oauth-protected-resource` or authorization server metadata exists. ChatGPT therefore cannot connect at all. Evidence: `api/mcp.ts:91-93`. Recommendation: an OAuth 2.1 authorization server (discovery metadata, dynamic client registration, PKCE, a consent page with read+write by default and delete as a separate option, refresh tokens).
- **COMPAT-2** (low, new) Tool results are only JSON text: no `structuredContent` and no `outputSchema`. Supported protocol versions stop at `2025-06-18`. Clients still work through fallback negotiation, but ChatGPT and newer clients render and chain structured results better. Evidence: `api/mcp.ts:13,70`.

## Candidate changes

1. **add-mcp-oauth-for-chatgpt**: addresses COMPAT-1, PERM-2 and PERM-1. It adds OAuth 2.1 for `/mcp` and a consent page whose default grant is read+write, with deletion of papers and answers as a separate permission. It filters the tool list by grant and adds delete tools behind that permission. A related feature from the developer could go here or in its own change: a tool that lets the model add its own Q&A pair to a paper, declaring its model name, recorded as "added via MCP" with a server-side timestamp. Behavior change: yes.
2. **improve-mcp-fulltext-fallback**: addresses ERR-1 and ERR-2. While doc2x is pending, `read_paper` returns a rough PDF text parse labeled non-precise, plus the arXiv HTML link when one exists, and tells the model to re-check on the user's next question. Paper tools report parse status and a next step. Behavior change: yes.
3. **streamline-mcp-tool-surface**: addresses RED-1, RED-2, DESC-1, DESC-2, PARAM-1, PARAM-2, ANN-1, ANN-2 and SIZE-1. It merges the admin and S2 edge tools, trims descriptions and instructions, aligns parameter names and strictness, fixes annotations and slims `get_topic`. Behavior change: yes. Renamed or merged tools affect existing clients and Paperland's own Codex allowlist.
