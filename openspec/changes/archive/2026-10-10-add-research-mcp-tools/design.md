## Context

- Research rounds call `callModel()` → `codex_provider.invokeAppServer()`, which spawns one `codex app-server` per invocation (stdio JSON-RPC), starts an ephemeral thread (`approvalPolicy: never`, `sandbox: read-only`), and streams the final answer.
- Verified against the real `codex` 0.162.1:
  - `thread/start` accepts `config: { mcp_servers: { <name>: { url, bearer_token_env_var } } }`; the server starts per thread, and the bearer token is read from the app-server process environment.
  - A Streamable HTTP server that answers every POST with `application/json` (no SSE, no session id) works. Tools with `readOnlyHint: true` are called without any approval request under `approvalPolicy: never` + read-only sandbox.
  - app-server emits `item/started` / `item/completed` for `mcpToolCall` items (`server`, `tool`, `status`).
  - `skills/extraRoots/set { extraRoots: [abs path] }` adds skill roots for that app-server process only (not persisted: a fresh process does not see them; `config.toml` unchanged). A cwd `.agents/skills` directory is also discovered (scope `repo`), but extraRoots needs no file copying.
- The user's own global MCP servers in `CODEX_HOME/config.toml` keep loading in research threads; we do not touch that file.
- S2: `semantic_scholar_service.ts` owns the key, the module-level rate gate, and backoff (`s2Request`); `s2_paper_cache.ts` owns `s2_papers` (`resolveS2Ids`, `upsertRecord`).
- Site data: papers are site-wide (behind the login wall); listed vs unlisted (`papers.listed`); personal library (`user_papers`); paper text via `resolvePaperContent()` (`content_priority`); Q&A visibility via `ownerVisibilityFilter(viewer, 'qa', …)`.
- The website login wall (`identityHook`) only guards `/api/*` and `/external-api/*`; other paths are public, so `/mcp` must authenticate itself.

## Goals / Non-Goals

**Goals:** read-only site + S2 tools over MCP; one token store (`api_tokens`) for the External API and `/mcp`; a per-user Codex agent token for Paperland's own runs and user-managed personal tokens for other MCP clients; no S2 key exposure; shared S2 rate limit; an S2 skill shipped in the repo; tool-call progress in the UI.

**Non-Goals:** write tools (adding papers, editing lists); giving tools to Q&A (the endpoint is caller-agnostic so it can be added later); full-text search (FTS5) — `search_papers` uses substring matching for now; the exec (`stream: false`) Codex path (research rounds use app-server models; exec rounds simply get no tools); token scopes beyond the two kinds; hashing stored tokens (the table already stores them in clear text).

## Decisions

- **Minimal MCP implementation instead of `@modelcontextprotocol/sdk`.** We need four methods over stateless JSON POSTs; the SDK's Streamable HTTP transport expects Node `IncomingMessage`/`ServerResponse` and session management, which fits Fastify/Bun awkwardly. A ~100-line handler (`api/mcp.ts`) with a tool registry (`services/agent_tools.ts`) is easier to test. Protocol version: echo the client's requested version when it is one we know (`2025-06-18`, `2025-03-26`, `2024-11-05`), else `2025-06-18`.
- **Path `/mcp`, outside `/api/`.** Avoids the cookie login wall (`identityHook` only handles `/api/*` and `/external-api/*`). It is reachable from anywhere, like the External API — the production reverse proxy forwards it too — and is protected only by the bearer token, so other MCP clients (a user's own Claude / Codex setup) can connect with a personal token.
- **One token store: `api_tokens` with a `kind` column** (migration `0037_agent_tokens`, additive): `personal` (default — existing rows) and `agent`. `rotated_at` records in-place resets. A partial unique index `api_tokens_agent_user_unq (user_id) WHERE kind = 'agent'` guarantees one agent token per user; `ensureAgentToken()` is `INSERT … ON CONFLICT DO NOTHING` + select, so concurrent calls stay idempotent. The migration backfills one agent token per active user (`'sk-' || lower(hex(randomblob(32)))`, same format as `newTokenValue()`); `db/index.ts` repeats that backfill at startup (covers the seeded admin). Pending users get none (rejecting a registration deletes the user row, which an FK from `api_tokens` would block; the delete also removes any tokens), so they get it on approval.
- **Who accepts which kind.** `services/api_tokens.ts#checkBearerToken(raw, kinds)` is used by `/mcp` with `['personal', 'agent']` and additionally requires an existing, active owner. `auth/token_auth.ts` (External API) adds "agent → 401" and "owner exists but is not active → 401" (same rule as `/mcp`), but still accepts owner-less legacy tokens, so Zotero and other existing integrations are unaffected.
- **Agent token secrecy.** No route returns an agent token value: `/api/auth/me/tokens` returns only `created_at` / `rotated_at`, the admin list returns `token: null` for agent rows and refuses to revoke them (400), and reset returns timestamps only. The value leaves the server only through the env of the Codex process Paperland starts.
- **Personal token self-service** (`api/tokens.ts`): list (masked), create (full value once), revoke own — every query is filtered by `request.user.id` and `kind = 'personal'`, so other users' tokens and agent tokens answer 404. The admin Settings list and issuance stay as they are.
- **Token delivery.** `ModelInput` gains `mcp_servers?: { name, url, bearer_token }[]` and `skill_roots?: string[]`. The Codex provider puts each token in the child env as `PAPERLAND_MCP_TOKEN_<NAME>` and references it with `bearer_token_env_var`, so the token never appears in the thread config payload or logs. The research runtime uses the session owner's agent token (`ensureAgentToken`), so a round started before a reset keeps the old value and its later tool calls fail with 401 — acceptable, and stated in the reset confirmation. Before `thread/start` it sends `skills/extraRoots/set` and waits for the reply.
- **Tool activity.** `ModelInvokeOptions.onToolCall?(e: { server, tool, status })` fires on `mcpToolCall` (and `webSearch`) item start/completion. The research runtime publishes an SSE `tool` event `{ step_id, server, tool, status }`; nothing is stored. The frontend keeps the latest event per active step and shows "Calling `<tool>`…" / "Searching the web…" in the step card while `queued`/`awaiting_output`/`streaming`.
- **S2 client exports.** `semantic_scholar_service.ts` exports `s2ApiGet(path, params)` (absolute path under `https://api.semanticscholar.org`, via `s2Request`). `s2_search`/`s2_match`/edges call it with a fixed field list; `s2_get` validates the path (prefix from config, regex `^/[A-Za-z0-9_\-./:%]+$`, no `..`, params as an object, never a raw query string).
- **Cache merge.** `s2_paper_cache.ts` exports `cacheS2Records(records)`: for each record with a `paperId`, merge into an existing `ok` row keeping existing non-null fields where the record's value is null/absent; insert when none exists. Partial records (search results lack `tldr`) therefore never erase richer rows. `s2_papers` uses `resolveS2Ids({ allowFetch: true })` directly.
- **Output shape.** Tool results are one text content item with compact JSON; abstracts in search/edge results are truncated to `research.abstract_char_limit` to keep context small. `read_paper` outline parses `#`-headings outside fenced code.
- **Skill** at `prompts/skills/s2-literature-search/SKILL.md` (next to `prompts/system/`), resolved by `agent_tools.skills_dir` (default: repo `prompts/skills`, absolute path computed from the backend module like `BUNDLED_SYSTEM_PROMPTS_DIR`). No existing S2 skill was found on the machine (`~/.codex/skills`, `~/.claude/skills`, `~/.agents/skills`), so it is written from scratch around our tool names.
- **search_papers scope.** Listed papers only (what the site's paper list shows); `get_paper` / `read_paper` work for any id so the agent can follow `in_library` links from `<paper_list>` even to unlisted papers.

## Risks / Trade-offs

- [The agent can burn S2 quota with many calls] → every call goes through the shared ~1 RPS gate, so it slows rather than 429s; the skill and prompt tell it to batch (`s2_papers`, one `s2_match` per title) and keep calls bounded.
- [Global user MCP servers also load in research threads] → harmless (read-only docs servers); avoiding it would require rewriting the user's config, which we must not do.
- [Token leakage] → tokens are read-only for `/mcp`; an agent token never leaves the server except into the Codex child env, and its owner can reset it in place at any time; personal tokens are revocable. Tokens stay in clear text in the DB, as before.
- [Codex protocol drift] → MCP config keys and `skills/extraRoots/set` are stable v2 API; if `skills/extraRoots/set` fails the provider logs and continues without the skill rather than failing the round.
