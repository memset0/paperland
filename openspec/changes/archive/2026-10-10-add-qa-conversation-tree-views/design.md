## Context

Q&A entries already form a follow-up tree (`qa_entries.parent_entry_id`, plus a `history` input naming the exact parent result). `GET /api/qa/entries/:id/tree` returns the whole tree around an entry with `parent_result_id` per node. The question box draft lives in the module-level singleton `useQAComposer` (text, attachments, follow-up target), already shared by the PDF viewer, answers, and `QAInput`. Live answers (polling + SSE streams) are held in `useQAStore().qaData` for the current paper/scope.

## Goals / Non-Goals

**Goals:** a derived-thread chat column with tabs and the docked shared question box; a mind map of the Q&A hierarchy; single-model asking.

**Non-Goals:** conversation/tree views on `/qa` or on narrow screens; storing threads server-side; backend or schema changes; changing the regenerate dialog (still multi-model).

## Decisions

- **Page layouts** — `useQAConversation` holds a global `layout` (`split` | `split-conv` | `three`, localStorage `paperland_paper_layout`) and the last conversation layout; `open` = layout ≠ split. Proportions live in the same composable as percentages of the split container (`paperland_paper_split_left` shared by split and split-conv; `paperland_paper_three` `{ left, conv }` for three columns), clamped on load and on drag (viewer ≥ 15 %, conversation ≥ 22 %, middle ≥ 25 %). Percentages (not px) are what fix the reload bug: the old px conversation width plus an unpersisted 45 % left column could squeeze or overflow the middle column after a reload at another window width. The paper info cards and the column are defined once with VueUse `createReusableTemplate` (`PaperColumn` with `part: all | metadata | qa`): the middle column renders `all`; in `split-conv` `PaperViewerPanel`'s optional `metadata` / `qa` tabs (slots) render one part each, the Q&A part owning the scroll container used by `QAPanelNav`. `revealQAEntry` / `locateBlock` bump a module signal that makes the viewer activate the Q&A tab first.
- **Conversation state** — new singleton composable `useQAConversation`: layout (above), and per user+paper `tabs: Array<{ entry_id, result_id } | { entry_id: null }>` + `active`, persisted in localStorage `paperland_qa_conv_<user>_<paper>`. A tab is just the thread's tail.
- **Thread resolution** — `QAThreadView` fetches the tail entry's tree once per tail, walks root → tail to collect the path, and pairs each ancestor with its child's `parent_result_id`. Content is taken from the live store entry (`qaData.template` / `qaData.free`, matched by `entry_id`) when present so streaming updates show, falling back to the tree snapshot. Hidden/deleted nodes render placeholders. Answers render through `QAResultBody` so streaming, citations, `#moonlight`, and actions behave as in the list.
- **Docked box** — `QAInput` gains a `docked` prop: no fixed positioning, move/resize grip, or close button. `PaperDetail` mounts exactly one `QAInput` (floating when the view is closed, docked inside `QAConversationPanel` when open), so the composer's caret inserter is always registered by the visible instance. While docked, the composer's follow-up target is driven by the active tab: a watch calls `composer.startFollowup` for the tail answer (or clears it for a new-conversation tab); the cancel-follow-up control is hidden. Submit is disabled while the tail answer is not `done`. After submit the active tab's tail becomes `{ entry_id, result_id: runs[0].result_id }`.
- **Routing existing entry points** — `useQAComposer.startFollowup` callers (answer 追问, `#moonlight`, `?followup=1`) go through a helper: when the conversation view is open it first opens/activates the answer's thread tab. `composer.openRequests` no longer opens the floating panel while the view is open.
- **Open in conversation** — `QAResultBody` gets an icon action (all statuses) emitting `openThread`, wired by `QAResultView` and `QAList`; shown only when the view is available (wide layout, logged in) via the composable's `available` flag set by `PaperDetail`.
- **Tree view** — `QATreeView` builds a forest from `qaData` (templates + free, current scope) by `parent_entry_id`; entries whose parent is absent become roots. It reuses the NoteMindmap layout technique (nested flex columns, SVG bezier connectors measured from DOM with a ResizeObserver) with a paper-title center node. It opens in a floating window from a button in the Q&A list headers; the list is not touched. Node click → preferred answer (pinned model else newest by request time) → open thread; fallback `revealQAEntry`.
- **Shared floating windows** — `stores/windows.ts` becomes the store of every floating window (`section`, `doc`, `qa-tree`, `qa-ask`): one z stack (starting at 200, above page chrome and the launcher FAB), one geometry model, per-kind size memory (notes keep their key; tree has its own; the question box none, placed with exact geometry via `place`). `components/FloatingWindow.vue` is the only shell: titled look (drag title bar, close) or `bare` look (slot content is the window, drag empty areas); both have the resize grip and go fullscreen on mobile. `FloatingWindowHost` (App.vue) renders note and tree windows; `QAInput` renders its own `qa-ask` window through the same shell because it needs page props and the docked mode. `closeForPaper` keeps closing only note windows (structural note changes), `closeKind('qa-tree')` runs when leaving a paper.
- **Single model** — `QAInput.toggleModel` sets `[name]`; the store trims `selectedModels` to its first valid element on load.

## Risks / Trade-offs

- Thread entries outside the current scope (e.g. others' shared ancestors under "mine") come from the tree snapshot and do not live-update → acceptable; they are normally finished.
- Tree fetch per tab switch → cached per tail in the component; refetched when the tail changes.
